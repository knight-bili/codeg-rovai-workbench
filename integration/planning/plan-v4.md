## 1 一期终点和范围约定

范围以本次固定源码版本为依据，不把上游持续新增功能无限叠加到同一截止日期。对固定版本中的漏项，一经发现立即补入一期；安全、数据丢失及兼容性修复进入整改任务。上游后续的新产品能力进入变更清单，由客户判断是否追加一期。重复功能可以统一实现，但不得丢失使用行为，也不能仅把两款应用放在两个窗口里作为融合交付。

“完整”指覆盖源应用的功能、配置、正常路径、异常处理和原生适用平台；“高可用”指在约定的单 Owner 本地或可信自托管部署中可靠恢复和长期运行；“高扩展”指新增 Runtime、渠道、预览器、技能和主题有稳定契约。当前用户没有提出多租户商业云、双活数据库或全球分布式部署，这些不能被擅自加入一期来扩大成本。

平台条件必须写清。手机作为 Host 客户端，不在手机上安装桌面 CLI；独立无头 Server 没有可共享的本机桌面时，电脑操作没有目标窗口。这属于源能力的运行条件，不等于把原生移动、远程入口或电脑操作移到二期。桌面功能的跨端入口和融合对象一致性仍需验证。

## 2 最终产品全景

最终产品以统一工作台呈现。无限画布是操作和组织空间；AI 队员是长期身份；Mission 是目标与交付；Thread 是公共协作记录；Task 是持续责任；Run 是单次执行；文件树、编辑器、终端、Diff 与 Git 是真实工程工作区。各入口引用同一 Core 对象，不能各自维护另一套任务状态。

D01 首次使用和统一工程入口。安装发现、依赖检查、工程打开、切换、克隆、初始化、关联目录、别名和首次真实任务。

D02 AI 队员和模型配置。长期队员身份、职责、准则、头像、模型、Provider、环境、权限及成员能力配置。

D03 Runtime 完整并集。保留两源内置 Runtime 和自定义 ACP；安装、认证、模型、执行和平台资格可见，不能仅保留枚举。

D04 Skills MCP 和专家包。原址发现、工具箱、安装和市场、专家技能、来源和版本、按队员分配及实际投递。

D05 无限画布。多画板、八种原有节点、布局、分组、文件和终端卡片，以及 Mission、Task、Thread 的统一引用。

D06 完整对话和历史。公共 Thread、单聊、草稿、附件、引用、检索、旧会话导入、标签、批量整理、分叉和插话。

D07 团队协作与交接。平级和负责人团队、动态成员、公开消息、指定接收者、异步委派、Task 分派与交接。

D08 Mission 和交付。目标、队伍、主 Thread、持续任务、Worktree、固定基线、累计 Diff、待验收、重试、合入、清理及 PR。

D09 执行控制。工具过程、时间线、证据、审批、问题回答、计划确认、精确停止、超时、失败恢复和有序关闭。

D10 记忆。共同、队员及队员间记忆，读取权限、修订、待审核、停止沿用、遗忘和导出。

D11 文件和编辑。文件树、搜索、真实文件操作、编辑保存、外部变化冲突、多标签、分屏、文件产物和预览。

D12 终端和工程命令。PTY、输入与缩放、快照、关闭、快捷消息、Shell 和工程命令；终端不是持久业务会话。

D13 完整 Git。分支、Worktree、暂存、提交、Diff、历史、远程、Stash、重置、merge/rebase 和三栏冲突解决。

D14 Forge。GitHub、GitLab、Gitea、Forgejo 面板及源支持的议题、评论、PR 读写、任务转换与来源关联。

D15 浏览器和电脑操作。共享网页、DOM/元素、截图、控制台、浏览器管理及共享原生窗口的查看和操作。

D16 Office 科研和交互卡片。docx/xlsx/pptx 实时预览、文献与实验统计技能、生成式 UI 和结果回传。

D17 自动化。定时、立即运行、运行历史、overlap、超时、取消、失败和结果通知，复用统一执行责任。

D18 用量和通知。Token、缓存、热力图、成本估算、来源与 Coverage、未读、提醒和错误恢复；未知数值不得当成零。

D19 Desktop Web 和独立 Server。同一 Core 的受控远程访问、认证、静态客户端、独立运行、容器、诊断和升级。

D20 渠道和用户 CLI。Telegram、微信、飞书、Lark、钉钉、Owner 授权、消息关联、结果回传与用户自动化入口。

D21 原生移动客户端。iOS/Android 手机和平板，保留源页面和行为，适配融合 Host、队员、Mission、Task 与 Thread。

D22 数据保护和系统维护。加密备份、WebDAV、恢复预检、回滚、启动诊断、日志、更新、deep link 和外部打开。

D23 全部个性化能力。源主题、语言、自定义 CSS、快捷键、减少动态效果、关闭行为、宠物管理、导入和市场。

23 个领域用于说明产品全景，附录的 81 个来源功能簇用于追踪移植归属。功能簇并不是 81 个按钮，也不能证明所有原子用例已经穷尽；I00 会将每簇展开为实际页面、命令和配置清单，I12 按该清单验收。展开清单发现固定基线漏项时必须补入一期，不能以本表没有列出为理由删除。

## 3 源码基础和架构实施

Rovai 保持 Electron Desktop、Rust Host、rovai-core 与 rovai-web 为主骨架。Codeg 的 React 界面、画布、工程和工具能力按模块移植；Tauri 命令改接统一 Host 的业务或宿主服务，不把 Codeg 完整数据库与执行引擎作为第二底座。iOS 与 Android 保留原生工程，通过网络客户端适配统一 Host。

业务链路为 Desktop／Web／原生移动／渠道／CLI → 统一操作网关 → Rovai Core → Runtime 和工程服务。浏览器、PTY、OfficeCLI、电脑 helper 属于宿主侧能力服务，执行请求带 Core 的 Actor、Run 和授权上下文。视图只能显示投影，不能绕过 Core 直接推进 Mission、Task 或 Run。

保留 Rovai 的 Mission 主 Thread 关系、Thread 内 Task、队员协作和恢复语义。Codeg 待办和委派映射到这些对象，必要字段通过 Core 迁移补齐。历史 CLI 会话可以作为来源记录导入；原生 session 标识继续作为 Runtime 内部标识，不冒充公共 Thread。

传输层先复用现有父进程管道、Host 和 Web 操作目录。UDS／NamedPipe 身份握手、公共 DTO 自动生成如有必要，在 I01 建立实施任务；它们在当前固定版本不能一律宣称已经完成。Host 的同数据根独占锁保持有效，独立 Server 不与 Desktop 同时作为第二写入者打开同一数据库。

| 模块来源 | 移植方式 | 必须解决的问题 |

| --- | --- | --- |

| Codeg 画布和工作区 UI | 复用 React 组件和行为，改接 Core DTO | 对象 ID、实时状态、路径和 PTY 生命周期 |

| Codeg ACP 与原生会话 | 拆出协议解析及能力投递，接 Rovai Adapter | 重复 Run、恢复、平台准入和公开输出边界 |

| Codeg 文件 Git Forge | 移植命令实现或复用 Rovai 等价服务 | 暂存区保护、冲突状态、凭据、失败和幂等 |

| Codeg 浏览器和 Computer | 适配 Electron 页面宿主，复用 driver/helper | Tauri 绑定、系统权限、授权失效和三平台差异 |

| Codeg Office 科研 UI 卡片 | 移植依赖管理、技能和渲染器 | 外部服务生命周期、来源、渲染隔离 |

| Codeg 备份 WebDAV 与个性化 | 迁移到统一数据模型和系统设置 | 数据库一致性、加密、清单版本和回滚 |

| Codeg iOS Android | 复用 SwiftUI／Compose，改网络层和对象映射 | 旧 REST／WebSocket 与新 Host 协议差异 |

| Rovai 渠道 Web CLI | 保留并补齐跨宿主运行契约 | Electron Main 渠道抽离、远程认证和共享业务状态 |



### 3.1 API 和事件设计

以下为拟实施契约，不是对当前源码已实现 API 的宣称。优先扩展 rovai-web 已有 operation catalog，使用统一的 command_id、actor、expected_version、operation 和 payload；有状态写命令返回 receipt、version 与 result_ref。查询返回 snapshot_version；重试复用 command_id，版本冲突必须返回明确冲突，不能静默覆盖。

| 操作族 | 范围与约束 | 实施阶段 |

| --- | --- | --- |

| 既有 members threads tasks missions agentRuns | 保持已有操作语义，补融合字段，不建立平行业务 API | I01 I02 I04 |

| canvas.boards 和 canvas.nodes 拟新增 | 布局 CRUD、对象引用、版本和删除对象处理 | I03 |

| history.import conversation.tags session.fork 拟新增 | 来源去重、标签关系、Runtime 能力判断和分叉来源 | I06 |

| workspace.files git.* forge.* 拟新增或复用 | 真实工程操作、影响预览、凭据引用和任务 PR 映射 | I05 I07 |

| browser.* computer.* hostServices.* 拟新增 | 授权目标、Run 归属、仅读／读写和撤销，不允许远程隐式授权 | I08 I09 |

| backups.* sync.webdav.* 拟新增 | 预检、加密、一致性快照、任务进度、失败恢复和回滚 | I11 |

| capabilities 和 protocol.version 拟新增 | 逐客户端、平台、Runtime 的能力及最小版本声明 | I01 I10 |



Core SSE 通知和快照保持权威。移动客户端原有 HTTP 和 WebSocket 网络层用版本化协议适配：旧增量事件投影到统一对象，重连先校验版本再读取快照；流式输出来自 Core 接受的 Run 事件。不得从原生客户端直接操作第二套数据库。PTY 使用独立受认证连接，关闭和断连回收由 Host 负责。

### 3.2 数据库和数据迁移

保留 Rovai 现有 SQLite schema、事务和迁移体系。以下为新增或扩展的逻辑模型，I01 对照现有表最终确定名称和字段；不预先强行创建与现有表重复的六表模型。工程目录及布局偏好仍采用当前适合的客户端配置，不能为了表格整齐再创建持久 project catalog。

| 拟新增或扩展的数据 | 关键字段和约束 | 来源和生命周期 |

| --- | --- | --- |

| 画板及节点 | board_id、node_id、kind、object_ref、geometry、version；对象引用不复制执行状态 | 持久布局；对象删除时处理失效引用 |

| 会话来源和导入映射 | source_runtime、source_key、source_path、content_hash、thread_ref、import_version；来源去重 | 只读原始会话；可重导和失败重试 |

| 标签及关系 | scope、name、thread_ref；唯一性和级联由统一 schema 决定 | 全局与工程范围可检索 |

| Forge 来源和 PR 关系 | provider、repo、issue_ref、pr_ref、mission_ref、task_ref；不存明文凭据 | 链接和交付事实持久；远端内容按需刷新 |

| 扩展配置及凭据引用 | runtime／channel／viewer 标识、版本、能力、secret_ref；复用现有配置入口 | 秘密在 keyring；备份策略显式选择 |

| 备份和同步任务元数据 | snapshot_version、manifest_version、checksum、状态和恢复计划 | 文件包与数据库版本一并验证 |

| 既有命令和运行事实 | 复用 command receipt、Actor、版本、Run 和恢复记录；必要时增补外部效果状态 | 一个 Core 写入权威，避免盲重放外部副作用 |



数据库迁移必须在隔离数据副本中验证：空库、新旧版本、失败中断、回滚和恢复。SQLite 备份必须保证一致性；直接复制仍在写入的 db 和 WAL 文件不算安全备份。新增画布、导入映射和 Forge 关联必须一并进入恢复测试。

### 3.3 Runtime 与平台兼容

源码目录经名称规范化得到 Codeg 15 类、Rovai 18 类，合并后 21 类内置 Runtime，再加自定义 ACP。名称归并仅用于清单，不能推定两源运行语义、平台支持或登录方式完全相同。

完整并集为：antigravity, claude_code, cline, code_buddy, codex, command_code, copilot, cursor, deepseek, gemini, grok, hermes, kimi_code, kiro, open_claw, open_code, pi, qoder, qwen_code, trae_cn, zcode。

Rovai 需补的 Codeg 独有入口为 Gemini、Hermes、OpenClaw 和自定义 ACP。Rovai 独有的 Copilot、CommandCode、Kiro、QwenCode、TRAE CN、ZCode 等同样保留。现有 NotQualified 平台需要有检查、整改、复测或证据充分的原生限制说明，不能只改枚举或跳过准入。

Runtime 矩阵包含发现、安装、认证、模型选择、消息与工具、审批、停止、恢复，以及源支持的分叉、插话和用量。外部 Runtime 未提供某能力时，显示具体原生限制；所有源支持的平台能力均进入一期。账号或外部版本造成的阻塞要有解决动作，最终验收不能以“未实测”关闭该项。

## 4 从初始化到完整 MVP 的排期

日期由脚本按周一至周五计算，不手算，不扣未约定的法定节假日。有效推进日指能够持续进行实施、自测和必要反馈处理的一天；此计划不代表会话关闭后仍会自动在后台持续开发。我们每次继续项目按仓库状态和待办推进，可用时段不足则实际日期平移。

各阶段都包含模块设计、编码、日常自测和该阶段已知缺陷修复。20 日预留是为跨模块、第三方、跨平台等额外风险准备，不能把所有测试都拖到最后。表中顺序按主要依赖安排，CI 构建和资源核实可提前；未授权新增开发团队或多代理并行，所以没有假设额外人力压缩工期。

## 8 GitHub 管理和客户验收流程

初始化主仓是第一个开发动作。默认私有仓保留上游来源和许可证；阶段任务用 Issue 和里程碑管理，代码进入阶段分支，本地通过相关检查后用中文提交。推送按客户既有要求获得授权；同意一次性开发分支推送后，不重复索要同一权限。多个仓库推送串行并保持间隔。客户验收通过后才推进 main 和发布标签。

每个模块任务经过待设计、待实现、自测中、待客户验收、已验收；遇到外部资源不足进入阻塞，不能进入已验收。PR 包含具体行为改变、测试证据、数据迁移、风险和演示入口，不带作者署名或工具水印。

每阶段给你可运行构建、简短操作路线、通过／失败清单和待确认的产品交互。你只需要验收使用行为和结果；研发分析、代码修复、测试补齐和仓库维护由我承担。单阶段验收反馈处理计入相应阶段或预留，客户反馈等待的日历时间另记，不伪装成开发完成率。

集中编译、回归、push和Actions。除已完成的I00初始化外，I01–I12按12个阶段验证批次安排；
具体规则及允许的缺陷补验见[阶段批量验证](../ci-cost-policy.md#阶段版本与验证频率)，版本见[阶段候选清单](stage-versions.json)。
不把CI等待变成当前编码的默认阻塞，也不以减少次数削减一期必需测试；最终main合入、发布标签和客户验收边界不变。

最终验收场景要贯穿产品：创建工程和队员 → 画布组织 → Mission 与 Thread 协作 → 导入会话及引用 → 多 Runtime 交接 → 文件和 Git 操作 → 议题转任务及 PR → 浏览器／原生应用工具 → Office／科研／交互卡片 → 自动化与多渠道 → Web 和双原生移动继续 → 备份同步恢复 → 崩溃恢复及升级。独立演示某个按钮不替代该连续场景。

## 9 计划自审结果和当前边界

本轮先做了计划自审再交付。检查结论：图中七组均为一期任务；81 个来源功能簇都有唯一主要实施阶段，零条默认移到二期；23 个产品领域对应任务和验收；48 个研发工作包与 13 个实施阶段及整改预留可追踪。排期天数和日期由脚本计算，无重复计入周末。

自审修正了三点：原生移动不只是 Web 页面，已补独立 SwiftUI 和 Compose 源码移植；Runtime 不能只保留 Rovai 目录，已补并集和自定义 ACP；高可用不能只写形容词，已补故障、长稳、性能、恢复和数据一致性目标。前版的“后续候选”划分及 18 至 30 日小范围排期不再作为执行依据。

可行性分析的总体方向继续有效，但不能表述为“已经没有风险”。最主要的不确定性是浏览器宿主、完整 Runtime 准入、渠道 Server 化、原生移动资源及备份迁移。现有源码支持采用复用和适配路线；当前没有证据表明必须取消这些功能，也没有完整构建和运行证据可保证初始日期一定兑现。

自审通过的是范围、任务、依赖、数字和交付标准的一致性，不是产品可用性证明，更不是独立第三方审计。待你确认的只是实施排期、验收节奏和必要资源安排；完整一期范围已经由你明确，不再重复询问是否纳入这些能力。
