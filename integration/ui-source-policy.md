# 一期全部页面的源码 UI 依据

客户于 2026-10-16 明确要求：每个页面都参考 Codeg 和 Rovai 原应用的源码 UI 设计，不作无依据的原创发挥；允许继续优化，但效果和使用体验不能比原应用更差。本规则覆盖整个一期 I00–I12 与 BUF，不只覆盖画布。

## 实施方式

1. 每个实际页面及复杂弹窗，先确认两份固定源应用中对应的页面、组件、样式和交互处理函数。使用已有 CodeGraph 索引查询，记录准确源码位置；源码版本以 `sources.lock.json` 为准。
2. 有明确对应的现成页面，优先复用原组件和布局。两边有同类页面时，按该页面承担的真实业务核对两套交互，再组合既有组件；Rovai Core 继续是唯一业务、执行和数据库权威。
3. 融合增加的入口、状态或弹窗，沿用对应原页面的组件和布局规则。常规实现选择由研发自行完成，确实改变模型输入或既定产品行为的方案仍按原治理要求处理，不能把本规则变成新的逐页客户确认门槛。
4. 保留原页面的完整操作、状态、可访问名称、键盘使用、错误反馈和恢复入口。界面整理不能省掉原功能，也不能用假数据、禁用的装饰按钮或示意内容冒充实际能力。
5. 优化必须说明要解决的具体问题，并用真实界面的同场景对照检查。代码和测试通过之后，仍需检查实际布局、字体、颜色、图标、信息层次、操作步骤、响应和功能完整性。存在会造成退步的差异时继续修复，不能以“风格不同”为由通过。
6. 页面容器须贴合实际工作区，避免外层默认留白、无意义的高度和重复滚动。只让确实超出的列表或正文承担滚动，保留全部内容的可达性；不得用统一隐藏滚动条或裁掉内容冒充修复。窗口变小时检查最后一项仍能到达。

## 每页工程完成的依据

| 依据 | 必需记录 |
|---|---|
| 原页面 | 对应源应用、固定提交、原组件/样式/交互位置 |
| 融合页面 | 实际路由和组件、保留及合并的入口、真实数据来源 |
| 优化 | 要解决的问题、具体变化、保留能力；没有优化时直接沿用原设计 |
| 运行对照 | 同状态截图、视口/缩放及必要的密度统一、关键操作结果 |
| 自审 | 可接受的真实业务差异、待修差异、错误/空/加载/恢复状态及窗口尺寸 |

这些是研发内部工程检查，不要求客户逐页执行技术测试。各阶段按既定批次集中构建和检查；I12 工程完成后再交客户作为真实用户使用验收。尚未进入实现阶段的页面继续按原工作包排期，不将全部后续页面提前塞进 I03。
